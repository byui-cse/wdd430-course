## Introduction

When you use AI to plan a larger project, the hardest part is not getting ideas. It is keeping the idea focused enough to turn into something your team can actually build.

A strong specification solves that problem. It gives AI a clear target, gives your team a shared source of truth, and makes it easier to judge whether the work still matches the original idea.

This activity walks you through creating that specification with a general model such as Copilot Chat. You will not use a special command set or a package of prebuilt prompts. Instead, you will learn how to ask better questions, review the model’s output critically, and refine the result until it is specific, testable, and useful.

## **01** Start With the Project Idea

Begin with a web application idea that your team could realistically build later in the course.

Before you ask the model to write anything, spend a few minutes defining:

1. The problem the application solves.
2. The people who will use it.
3. The core workflow those users need.
4. Anything the project should not try to do yet.

If you skip this step, the model will usually fill the gaps with generic features and extra scope. A few minutes of planning here makes the rest of the activity much easier.

## **02** Draft the Specification With AI

Use a general model to help you draft the specification. Your goal is not to let the model invent the project for you. Your goal is to give it enough context to produce a useful first draft that you can edit.

A good first prompt should ask the model to act like a planning partner. Tell it to ask clarifying questions first, then draft a specification once it has enough context.

Example prompt:

```text
Help me write a project specification for a team web application.

First, ask me the minimum set of clarifying questions you need about:
- the problem the app solves
- the intended users
- the core features
- the data the app needs to store
- the key screens or views
- anything that should be out of scope for now

After I answer, draft a specification with:
- a short project description
- target users
- MVP features
- optional or future features
- basic user flows
- initial data models
- important API endpoints or interactions
- any open questions that still need decisions

Keep the specification practical and student-friendly. Do not add implementation details like frameworks or deployment plans yet.
```

After the model gives you a draft, review it for these problems:

- vague features that could mean three different things
- missing users or use cases
- hidden implementation details that should wait until later
- features that are too large for a single student team to finish
- unclear data models or missing relationships
- missing edge cases such as empty states, errors, or permissions

A strong project specification should usually have:

- A clear description of the problem and why it matters.
- The users or audience the project is for.
- A concise MVP with features that are actually buildable.
- Additional features that can wait until later.
- Initial data models with the important fields and relationships.
- The main screens, flows, or views the user will see.
- The API endpoints or interactions the app will need.
- A short list of open questions or assumptions.

The spec should be detailed enough that someone unfamiliar with the project can understand what is being built, but it should still leave room to choose the technology stack later.

## **03** Critique and Improve the Draft

Do not accept the first draft as finished. Use the model to help you review the specification the same way a teammate would.

A useful follow-up prompt looks like this:

```text
Review this project specification and point out:
- any vague or testable requirements
- any missing user types or use cases
- any scope that feels too large for an MVP
- any implementation details that should be removed
- any missing data models, views, or API interactions

Then suggest specific revisions.
```

If the model points out problems, edit the specification manually and ask for one more pass. You are looking for a document that is clear, realistic, and narrow enough to support a real project.

## **04** Use the Spec as a Shared Reference

Once the specification is solid, save it and treat it as the source of truth for the project idea.

Later in the course, your team will use that specification to help compare technology choices and to keep implementation work grounded in the original goals. The specification should answer the big questions first: what the app does, who it is for, and what counts as done.

If you find yourself adding stack decisions, deployment plans, or feature implementation details too early, stop and move those ideas to a later planning step.

## **05** Exercise

Write a specification for one project idea you could realistically build in this course.

### Steps

1. Choose a project idea and write a short summary of the problem it solves.
2. Use a general AI model to ask clarifying questions and draft an initial specification.
3. Review the draft and remove anything vague, overly large, or implementation-specific.
4. Add the missing pieces: users, MVP features, optional features, data models, views, and API needs.
5. Write down any open questions that still need answers.
6. Save the final specification so you can reuse it later when your team starts planning the build.

### Reflection

Write 5-8 sentences about:

- What question from the model helped you clarify the project most?
- Where did the first draft overreach?
- What did you have to edit to make the spec more realistic?
- What would have gone wrong if you had skipped the review step?

## **06** What Comes Next

In a later activity, you will turn a solid project idea into a more detailed implementation plan. That next step is where technology choices, feature slicing, and task breakdowns start to matter more.

For now, focus on making the specification clear enough that your team could still make good decisions later, even if the stack changes.
